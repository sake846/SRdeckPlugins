# STD-T98 4FSK受信・標準秘話解析の改善と評価

2026-09-09。4FSK受信、軟判定FEC、標準秘話解析とIQ評価の改善をまとめる。
本書は合成入力と実録音の比較結果を示す。実機感度や自然会話の解読成功率を示すものではない。

## 2026-10-11: 弱い実録音に対する位相弁別の改善

4FSKの位相差を1サンプル間隔から5サンプル間隔（約104 µs）へ変更した。
低振幅区間の急な位相変化が復調フィルタへ入る影響を抑え、増えた2サンプルの遅延はフレーム時刻から差し引く。
同期・CRC・候補再試行の受理条件は変更しない。履歴は入力ブロックをまたいで保持し、リセット・非有限入力で消去する。
位相差の非曖昧範囲は±4.8 kHzで、ホストの阻止帯域端±4 kHzを包含する。
入力は引き続き選局・帯域制限済み48 kHz IQを前提とする。

AppDataの20秒・960000サンプルの実録音を比較した。元のWAV・JSON・gainは変更していない。
WAVのSHA-256は `719EB1BC17C3631682F7D56BA416E87D3C00EB448C0BC72BA09FA27FD99ACDFD`。

| 診断指標 | 1サンプル間隔 | 5サンプル間隔 |
| --- | ---: | ---: |
| CRC通過フレーム | 16 | 26 |
| 音声20 ms区間 | 64 | 104 |
| 硬判定FEC訂正数0の音声区間 | 16 | 26 |
| 未保護ビットの信頼度不足区間 | 55 | 94 |

従来の16フレームはすべて同じ制御情報で維持した。**音声の欠落・誤りは依然多い。**
正解の音声ビットがないため、CRC通過や訂正数0を正常音声・BERの証明として扱わない。
秘話鍵・通信内容の解析や音声合成はこの受信比較には不要。

独立した合成入力も11条件×2経路×10試行×5方式、1100測定で比較した。
各条件の期待値は120フレーム・480音声区間。下表は `three-soft` と `lagged-soft` の比較。

| 条件 | 正常フレーム（旧→新） | 正解AMBE完全一致区間（旧→新） |
| --- | ---: | ---: |
| 直接入力 AWGN 6 dB | 97→120 | 366→434 |
| ホスト経由 フェード 12 dB | 105→108 | 415→424 |
| ホスト経由 AWGN 3 dB | 120→120 | 436→433 |
| ホスト経由 AWGN 0 dB | 120→120 | 254→250 |
| ホスト経由 インパルス 12 dB | 85→84 | 323→319 |
| 直接入力 インパルス 12 dB | 111→95 | 444→377 |

9 dB以上のAWGNは両経路とも480区間すべて完全一致。新方式の制御情報誤受理は全条件で0件、
雑音のみ・隣接波のみでも0件だった。全条件の改善ではなく、帯域制限前のインパルスでは低下がある。
ホスト経由12 dBの平均受信処理は約1秒の入力あたり3.79→4.01 ms。この計測は実機の総CPU負荷を表さない。
比較結果はローカルの `temp/t98-lag5-benchmark/reception.json` と `reception.csv` に保存した。

```powershell

```

先頭最大20秒を読み、件数・同期誤差・周波数ずれ・FEC診断・入力ハッシュを `capture-reception.json` に出力する。

検証: Releaseビルド（警告・エラー0）、STD-T98回帰48件成功。
`ARIB STD-T98 delayed discriminator` は既知の送信ビット列について±1800 Hz・IQ反転・120 ppm・
一括/1/317サンプル入力の完全一致、時刻、リセット、非有限入力、弱信号の回収、雑音・隣接波拒否を検証する。
`ARIB STD-T98 capture evaluation` は生成WAVによる新旧診断の比較を検証する。
実録音比較は正解ビットを持たない補助評価で、実機からの新たな受信・聴取試験は未実施。

## 2026-10-12: 既知ビットによるTCH BERと理論基準

実録音には送信側の正解ビットがないためBERを測れない。そこで、生成時の全ビットが既知の合成IQを使い、
CRCを通過して制御情報・フレーム位置が正解と一致した通信フレームのTCH 288ビットを、AMBE FEC前に比較した。
TCHのPN9スクランブルは受信器の出力と送信側正解の両方で解除済み。欠落フレームはBERの分母に含めず、受信率を別に記録する。

Release試験DLLでAWGNを各SNR・各入力経路10試行実行した。ホスト経由では各SNRで期待120フレームをすべて受信し、
比較ビットは34,560（120×288）。旧`three-soft`と5サンプル位相差の`lagged-soft`を比較した。

| 複素IQ SNR | 旧 three-soft | 5サンプル lagged-soft | 理想4値判定基準 |
| ---: | ---: | ---: | ---: |
| 0 dB | 810/34,560 = 2.3438% | 816/34,560 = 2.3611% | 0.17542% |
| 3 dB | 98/34,560 = 0.2836% | 101/34,560 = 0.2922% | 0.0024245% |
| 6 dB | 3/34,560 = 0.008681% | 5/34,560 = 0.01447% | 0.000000627% |
| 9 dB | 0/34,560 | 0/34,560 | 5.88×10⁻¹⁶ |
| 12 / 18 dB | 各0/34,560 | 各0/34,560 | さらに小さい |

0 dBと3 dBでは新方式の誤り数が旧方式より6 bit、3 bit多く、6 dBでは2 bit多かった。これは少数の合成seedに対する結果で、
BER改善は確認できていない。直接入力の6 dBでは旧方式が97/120フレーム・78/27,936 bit、新方式が120/120フレーム・
119/34,560 bitを受信した。新方式は受信フレームを増やしたが、受信済みビットのBER点推定は0.2792%から0.3443%へ増えた。
したがって本変更の効果は弱信号での同期・フレーム捕捉にあり、ビット判定精度そのものの改善とは分けて扱う。

理論曲線は、等確率の実数レベル−3/−1/+1/+3を独立ガウス雑音に通し、最近傍のしきい値−2/0/+2とSTD-T98のGrayラベルで
硬判定した4値PAMのBERをガウスCDFで数値計算したもの。SNR軸からの`Eb/N0 = SNR + 10 dB`は48 ksample/sと4800 bit/sからの
名目換算であり、受信フィルタ後の実効雑音帯域を測った値ではない。STD-T98の実波形は整形4FSKと位相弁別器を通るため、
このPAM理論は実方式の厳密な理論曲線ではない。理論値が測定値を大きく下回る差はこのモデル不一致を含み、実機性能差として解釈しない。

9 dB以上で誤りを観測しなかったことも、BER=0の証明ではない。34,560 bitで誤り0件の場合、二項分布の片側95%上限は約
8.68×10⁻⁵（0.00868%）。CSVは観測BERの0とこの上限を別列に記録し、SVGでは上限位置へ点を描く。
JSON/CSV/SVGは`temp/t98-ber/`へ出力。再実行コマンド:

```powershell
dotnet run --project SRdeck.Tests/SRdeck.Tests.csproj -c Release --no-build -- --benchmark-arib-t98 temp/t98-ber 10 --receive-only
```

## 変更内容

- 同期の最良候補が失敗した場合、2サンプル以上離れた近傍候補を最大2つ再試行する。追加候補は、
  直前の正常フレームと3700～3980サンプルの間隔、通信種別、モード、SACCH全情報ビットが一致する場合だけ採用する。
  CRC-6だけを条件とする再試行は比較中に誤受理を増やしたため採用しなかった。新しい通話や制御情報の変化は第一候補で受信する。
  既存のgain/offset/slicingErrorしきい値は維持し、試行数・回収数・最大試行数を計測する。
- TCHの288ビットに符号判定の信頼度を付け、PN9解除後も同じビット順でAMBEへ渡す。正負と内外の
  最短距離差を雑音分散の推定値で規格化した相対信頼度であり、校正済みBERではない。
  mbelib-neoの軟判定Golay復号を使い、信頼度のない既存フレームは硬判定で扱う。
- 同一フレームのFEC結果を弱参照のキャッシュで再生・プリセット選択・手動解析から共有する。PN15解除前の結果を保持し、
  コピー後に鍵を適用する。フレームのビット配列は構築後に変更しない。手動解析用スナップショットは信頼度も複製する。
  C0/C1の**符号語全体**が正しい場合は重み付き不一致コストが0になるため、軟判定の全探索を省略する。
  訂正数0だけではパリティ誤りを見逃すため、短絡の条件には使用しない。
- FECで保護されない25ビットの最小信頼度が32未満の音声区間は秘話推定から除外する。
  これは16倍で量子化した相対対数尤度の約2に相当する暫定値。音声再生には復号結果を使用する。
- 通常音声・無音・有効トーン・消失をネイティブCODECに合わせて分類する。`b0=124/125`の有効無音を
  無効値として減点せず、無音・トーン・消失の前後で音声予測状態をリセットする。
- 通常音声の解析開始には12フレーム・48区間・32隣接組を要求する。候補ごとにも32以上の実際の音声遷移を要求する。
  20フレームまたは64区間に満たない早期判定では、全体と前半・後半の全てで次候補比8以上、無効ピッチ0、
  ピッチ順位32以内、スペクトルと生ビットの連続性が1位であることを追加要求する。根拠が弱い入力は収集を続け、十分な音声では従来の判定条件を使用する。
  転記には全体の既存の順位・分離条件に加え、時間順の前半・後半で同じ最有力候補、各半分12音声遷移以上、
  3種類以上の音声パラメータを要求する。入力の連続区間数・最長区間・除外数と、保留の理由を表示する。
  二つの時間窓は整合確認であり、統計的な独立性や鍵の認証を意味しない。手動解析の候補は自動適用しない。
  自動探索は現在鍵、最大5件のプリセット、全32767コードの順に進める。現在鍵と単独プリセットは直ちに試行し、
  同じ時間窓の条件で発見したコードを現在鍵へ自動設定・保存する。全コード比較は受信処理を止めないようバックグラウンドで実行する。

分数タイミングは比較用の内部モードとして保持する。同期誤差の放物線補間で±0.5サンプル補正する方式を評価したが、
インパルス条件で音声ビット誤りが増えたため既定では無効とした。継続的なクロック追跡の追加は今回の採用範囲に含めない。

## 再現手順

Windows x64、.NET 10、同梱ネイティブCODECを使用する。リポジトリのルートで実行する。

```powershell
dotnet build SRdeck.Tests/SRdeck.Tests.csproj -c Release
dotnet test SRdeck.Tests/SRdeck.Tests.csproj -c Release --no-build --filter "DisplayName~ARIB STD-T98"
dotnet run --project SRdeck.Tests/SRdeck.Tests.csproj -c Release --no-build -- --benchmark-arib-t98 temp/t98-evaluation 10
```

`reception.json`、`reception.csv`、`privacy.json`を生成する。受信だけなら最後に`--receive-only`を付ける。
秘話だけなら`--benchmark-t98-privacy temp/t98-privacy 10`を使う。試行数は1～1000。
JSONにseed、入力条件、実行時情報、プラグイン・ネイティブDLL・試験DLLのSHA-256を記録する。
未コミットの差分がある場合も、アセンブリのGitバージョンだけに依存せず実行バイナリを特定できる。

受信比較は1試行12フレーム、seed `981000 + trial`、初期位相`trial × 3.75 mod 20`サンプル。
周波数ずれは0/+475/−600 Hz、クロック偏差は0/+120/−120 ppmを試行順に組み合わせる。
全組合せを網羅する掃引ではない。同じIQを次の5方式へ入力し、測定順は試行ごとに回転する。

| 方式 | 同期候補上限 | AMBE | 分数位相 |
| --- | ---: | --- | --- |
| single-hard | 1 | 硬判定 | なし |
| three-hard | 3 | 硬判定 | なし |
| three-soft（旧方式） | 3 | 軟判定 | なし |
| fractional-soft（比較用） | 3＋分数位相1回 | 軟判定 | あり |
| lagged-soft（既定、5サンプル位相差） | 3 | 軟判定 | なし |

`single-hard`は現行コード内で追加候補と軟情報を無効にした比較方式で、変更前バイナリそのものではない。
入力は受信器への直接48 kHzと、ホストの`StandardChannelProcessor`を通す経路の2種類。
後者は48 kHz入力で6250 Hz帯域・8000 Hz阻止帯域の要求を処理する。SDRの高サンプルレートからの間引きは対象外。

SNRは**48 kHz入力の搬送波電力／複素白色雑音電力**。搬送波振幅0.6に対し、I/Q各成分の雑音標準偏差は
`0.6 / sqrt(2 × 10^(SNR/10))`。整形済み4FSKの既知試験音に18/12/9/6/3/0 dBのAWGNを加える。
さらに12 dBで、1フレームを振幅5%にするフェード、3840サンプルごと3サンプルのインパルス、
6250 Hz離れた振幅3倍の同じ変調波を評価する。負例は雑音のみ・隣接波のみ。多重波・自然会話はこのIQ生成器では模擬しない。

正しい制御情報と受信位置ごとに受信数を数え、重複・誤った制御情報を誤受理として別集計する。
AMBEは既知の49ビットと比較し、**受信できた区間だけ**の誤り数と比較ビット数を両方保存する。
未受信区間を誤りゼロにしないよう、欠落／不一致区間の20 ms換算と最長連続欠落も出力する。これは聴感的な音切れの測定ではない。
初回フレームの待ち時間は997サンプル単位で入力を届けた時点で計測する。
処理時間は受信処理とAMBE/FECを分け、受信ブロックのp95/p99、割り当て量も保存する。

受信成功率の95% Wilson区間は、同一試行内の相関するフレームを独立と見なさず、seed別試行を単位とする。
誤受理0件でも短い負例入力だけで低い誤受理率を証明できないため、0件時のPoisson上限も保存する。
時間値は機種・OS負荷・JIT/GCで変動する。秘話試験にはプロセスCPU時間も記録する。
通常CIでは固定入力の機能回帰を検証し、測定時間から受信改善の合否を決めない。
既存の実時間倍率テストも共有Runnerでは`SRDECK_TEST_TIMING_ASSERTIONS=0`で時間判定だけ無効にできる。

## 10試行の測定例

Releaseビルドで11条件×2入力経路×10試行×4方式、計880測定を実施した。各行の期待値は120フレーム・480音声区間。
同じビルドでSTD-T98回帰テスト28件が成功し、ビルドの警告・エラーは0件だった。
ローカルの測定結果は`temp/arib-t98-improvements/final-10/`、テスト結果は
`SRdeck.Tests/TestResults/arib-t98-improvements.trx`に保存した（いずれもGit管理対象外）。

| 入力・条件 | single-hard 正常フレーム／完全一致AMBE | three-hard | three-soft | fractional-soft |
| --- | --- | --- | --- | --- |
| ホスト経由 AWGN 0 dB | 118 / 251 | 120 / 253 | 120 / 254 | 120 / 254 |
| ホスト経由 AWGN 3 dB | 120 / 436 | 120 / 436 | 120 / 436 | 120 / 441 |
| ホスト経由 AWGN 6 dB | 120 / 479 | 120 / 479 | 120 / 479 | 120 / 480 |
| 直接入力 AWGN 6 dB | 96 / 363 | 97 / 366 | 97 / 366 | 97 / 366 |
| ホスト経由 インパルス 12 dB | 85 / 323 | 85 / 323 | 85 / 323 | 85 / 322 |

ホスト経由0 dBで、同じ120フレームを受信するthree-hardとthree-softを比較すると、
音声パラメータ誤りは341から314ビットへ減った（どちらも比較23520ビット）。
一方、直接入力6 dBでは28から34へ増えており、軟判定による全条件の改善は確認していない。
同期候補の追加でホスト経由の2フレームと直接入力の1フレームを回収した。
直接入力6 dBで制御情報の誤受理が全方式に同じ1件あり、再試行による増加は0件だった。
雑音のみ・隣接波のみの条件では全方式で誤受理0件。これらはこの短い試験条件での結果に限る。

ホスト経由12 dBで、約1秒の入力あたりthree-softの平均受信処理は6.23 ms、
AMBE/FECは0.18 msだった。軟判定を常に全探索した開発途中の約100 msから、
符号語検査による省略で良好な信号の計算量を抑えた。0 dBでは同処理が65.67 msとなり、弱い信号では全探索の負荷が残る。
受信キューを含む実機全体の遅延・消費CPUを保証する測定ではない。

秘話の別条件試験はseed `982000 + trial`で、回帰試験の固定鍵5931とは異なる鍵と合成パラメータを使用する。
これはFEC**後**の49ビット入力であり、自然会話や無線伝搬を模した試験ではない。
`bit-errors`はFEC後のパラメータに12回のビット反転を加える。

| 条件 | 正解が第1候補 | 正解が上位5候補 | 転記可能 | 誤転記 | 保留 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 合成通常音声 | 10/10 | 10/10 | 10 | 0 | 0 |
| 無音8区間を含む | 10/10 | 10/10 | 10 | 0 | 0 |
| 音声・データ混在 | 10/10 | 10/10 | 0 | 0 | 10 |
| 短い入力 | 0/10 | 0/10 | 0 | 0 | 10 |
| 隣接しない断片 | 0/10 | 0/10 | 0 | 0 | 10 |
| 同一音声の繰り返し | 10/10 | 10/10 | 0 | 0 | 10 |
| FEC後のビット誤り | 9/10 | 9/10 | 6 | 0 | 4 |
| 途中で鍵が変化 | 対象外 | 対象外 | 0 | 0 | 10 |
| 無作為ビット | 対象外 | 対象外 | 0 | 0 | 10 |

混在では短い音声の連続区間しかなく、正解が最上位でも転記条件を満たさなかった。
誤転記0/10のWilson 95%上限は約27.8%であり、この件数で低い誤推定確率を主張できない。
しきい値調整用の合成条件とは別のseedで確認したが、自然会話・話者・機種別の較正は未実施。

## 既知鍵の実機IQで確認する

プラグインが保存する選局済みWAV（PCM16、48 kHz、左I／右Q）をそのまま使える。
次のJSONをローカルに用意する。`WavPath`はマニフェストからの相対パスまたは絶対パス。
`KnownKey`は送信側で確認した標準PN15鍵、`UserCode=0`は全UC。機種と条件は実際の記録に置き換える。

```json
{
  "WavPath": "capture.wav",
  "KnownKey": 129,
  "ReceiverModel": "使用した無線機名",
  "Conditions": "既知鍵での通常会話、受信条件、録音日時",
  "UserCode": 0,
  "StartSeconds": 0,
  "DurationSeconds": 8
}
```

```powershell
dotnet run --project SRdeck.Tests/SRdeck.Tests.csproj -c Release --no-build -- --analyze-t98-capture temp/t98-manifest.json temp/t98-capture-result
```

1回に読み出す区間は最大20秒。最大100フレーム／8秒ごとの解析窓へ分割し、UC・製造者・通話の変化や長い欠落でも区切る。
5方式の受信診断と、既知鍵に対する第1候補／上位5候補の正否、転記可否、誤転記、除外区間数を
`capture-evaluation.json`へ出力する。入力WAVを変更せず、IQ・PCM・鍵の数値・候補コードを結果へコピーしない。
